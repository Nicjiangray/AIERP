# AIERP 系统设计文档
> AI驱动业务逻辑的轻量ERP · 工作版本

---

## 1. 系统定位

从零开始，用AI驱动业务逻辑的轻量ERP。

**核心思想：规则在数据库里，不在代码里。业务变了，改宪法表，不改代码。**

> 💡 **Claude建议**：这个定位非常清晰。补充一点——"轻量"的边界需要提前定义清楚：是指用户数量轻量（<100人），还是业务模块轻量（仅核心销售/采购），还是技术架构轻量（无需专职DBA）？这会影响后续的技术选型和性能预期。

---

## 2. 整体架构

系统分为四层：

| 层级 | 名称 | 作用 |
|------|------|------|
| 第一层 | 宪法表（4张） | AI理解业务的规则基础 |
| 第二层 | 基础表（若干） | AI理解产品、人员及组织架构 |
| 第三层 | 业务表（若干） | AI建立事件、跟进、数据更新、状态机锁定 |
| 第四层 | 向量记忆库 | 存储原始证据，支撑AI判断溯源 |

---

## 3. 宪法表（Constitution Layer）

> 系统的"基本法"，所有AI行为的规则来源。

| 中文名 | 数据库名称 | 内容 | 目的 |
|--------|-----------|------|------|
| 表单一览_主表 | `meta_tables` | 所有表的集合 | AI能够知道每张表的用处 |
| 表单细节_副表 | `meta_fields` | 每张表的字段解释，与其他表的关系 | AI能够准确写出SQL，不会报错 |
| 事件规则_主表 | `meta_rules` | 所有事件的集合，一个事件就是一个大业务流程 | AI理解每种事件的目的、发生条件、状态标记、描述等，依据规则建立事件清单 |
| 事件规则_副表 | `meta_task_templates` | 每种事件（每个业务）的关键要素及关键节点 | AI依据此表制作每个事件的todo list，是AI工作的核心约束条件 |

> ⚠️ **Claude建议（命名修改）**：原名 `meta_task_buffer` 改为 `meta_task_templates`。原名含"buffer"，与业务表里的 `task_buffer`（事件实例表）极易混淆。宪法表存的是"模板定义"，业务表存的是"运行实例"，名称应明确区分。

> ⚠️ **Claude建议（新增字段）**：在 `meta_rules` 里建议加入**事件唯一性条件**字段，用于定义"这条输入应归入已有事件还是新建事件"的判断标准。例如：`同客户 + 同产品 + 30天内 = 合并；否则 = 新建`。如果缺少这个字段，AI在第二步"检索记忆库"时没有明确的判断依据，容易产生歧义。

> 📌 **Claude建议（版本控制）**：宪法表需要版本控制机制——每次修改留记录，并且每一条AI判断日志都应存储 `constitution_version_id`，确保出问题时能完整还原当时执行的是哪套规则。

## 4. 基础表（Master Data Layer）

> AI认识人、产品、组织的数据基础。

| 中文名 | 数据库名称 | 内容 | 目的 |
|--------|-----------|------|------|
| 员工表 | `employee` | 记录所有员工信息 | AI认识员工，知道员工角色，根据角色控制权限 |
| 联系人表 | `contacts` | 记录所有外部联系人 | AI认识外部人员，知道所属公司，是事件核心组成部分 |
| 联系人偏好记录 | `contacts_terms_log` | 记录外部联系人的偏好 | AI记录和维护，提供证据，并做出建议 |
| 产品表 | `products` | 记录公司销售的所有产品 | 是事件的核心组成部分 |
| 客户表 | `customer` | 记录所有客户 | 是事件的核心组成部分 |
| 供应商表 | `suppliers` | 记录所有供应商 | 是事件的核心组成部分 |

> 💡 **Claude建议**：`contacts` 原文拼写为 `concats`，建议修正为 `contacts`，避免日后开发时的混淆。

---

## 5. 业务表（Transaction Layer）

> AI建立、跟进、锁定每一个业务事件的运行记录。

| 中文名 | 数据库名称 | 内容 | 目的 |
|--------|-----------|------|------|
| 事件记录表 | `task_buffer` | 建立每一个事件，由日期+发起人+产品+供应商/客户+目的等关键要素构成。不齐备的可用"？"替代，日期和发起人必须有 | AI获得关键要素后建立、查询、跟踪事件；信息不齐备时可主动询问是否建立事件 |
| 事件跟进表 | `task_steps` | 依据宪法中的事件副表（模板），生成标准的todo list | AI负责更新维护汇报todo list，提醒业务员跟进 |
| 附件证据表 | `attachments` | 每一步操作的依据来源：对话文本、邮件、Excel文档、图片、PDF | AI每次操作都有来源，并每日汇报 |

## 6. AI完整工作流程（8步）

```
第一步：收到任何输入
        ↓
第二步：检索记忆库
        有相关事件 → 归入已有事件，补充信息
        没有       → 跟用户确认，新建事件A
        ↓
第三步：事件A存入事件库
        原始资料、时间、来源全部打包存入
        ↓
第四步：查宪法表
        meta_tables          → 匹配意图，找到目标表
        meta_fields          → 理解字段，核对信息
        meta_rules + meta_task_templates → 找到规则和操作顺序
        ↓
第五步：制作TODO list
        列出所有步骤，标记状态
        待处理 / 进行中 / 完成 / 阻塞
        ↓
第六步：循环推进
        缺信息   → 追问用户
        条件满足 → 执行下一步
        用户废弃 → 标记事件作废，保留记录
        ↓
第七步：所有步骤完成，用户最终确认
        ↓
第八步：锁定数据，写入业务表，只读
```

> 💡 **Claude建议（第二步细化）**：第二步"检索记忆库"的判断标准需要显式定义，建议在 `meta_rules` 中增加"事件唯一性条件"字段（见第3节建议）。否则AI在模糊情况下无规则可循。

> 💡 **Claude建议（判断日志）**：每次AI做出判断时，必须记录：①依据了哪条规则（`rule_id`）；②使用的宪法版本（`constitution_version_id`）；③输入内容的摘要。这是日后审计和排错的基础。

## 7. 锁定机制（Immutability Layer）

### 锁定级别

| 级别 | 触发条件 | 修改方式 |
|------|---------|---------|
| 普通锁定 | 事件进入"已确认"及以上状态 | 需要管理员权限，必须记录修改原因 |
| 完全锁定 | 财务数据、合同金额等核心字段 | 不能修改，只能新建更正单 |

### 状态机（升序排列）

```
意向 → 商议中 → 已确认 → 已下单 → 已完成
```

> ⚠️ **Claude建议（顺序说明）**：状态机应按**升序**排列（低→高），代码实现时用数字映射（意向=1，商议中=2，已确认=3，已下单=4，已完成=5）。权限规则为：低权限角色无法修改高于某个阈值的状态数据。原文为降序排列，实现时注意方向。

> 💡 **Claude建议（状态不可跳跃）**：建议在 `meta_rules` 中增加状态转换规则，规定状态只能逐级推进，不能跳级（如不能从"意向"直接跳到"已下单"）。跳级操作需管理员审批并留记录。

## 8. 向量记忆库

**定位：不是模糊搜索工具，是证据库和事件归属引擎。**

四大核心功能：

1. **存储原始证据** — 图片、文字、表格、合同，一切原始输入均存入
2. **事件归属判断** — 判断"这条信息属于哪个事件"
3. **回溯查询** — 某年某月发生了什么，证据是什么
4. **判断溯源** — AI每个判断必须有出处，可追查

> 💡 **Claude建议**：向量库的"事件归属判断"（第2项）与第6步工作流中的"检索记忆库"是同一件事，建议统一表述，避免实现时产生歧义。具体来说：输入 → 向量库检索相似事件 → 结合 `meta_rules` 的唯一性条件 → 判断归属或新建。

## 9. 重要补充建议

### 9.1 宪法表版本控制（原有）
每次修改留记录，出问题能追溯到是按哪个版本执行的。

**补充**：每条AI判断日志中存储 `constitution_version_id`，确保完整复现当时的执行逻辑。

### 9.2 AI判断日志（原有）
每次判断的依据是哪条规则，必须记录。

**补充**：日志结构建议包含：`log_id`、`task_id`、`rule_id`、`constitution_version_id`、`input_summary`、`decision`、`timestamp`、`operator`（人工/AI）。

### 9.3 从最小闭环开始验证（原有）
先把"新员工入职"这一个场景完整跑通，验证逻辑可行，再往外扩展。

**补充**："新员工入职"覆盖了五个核心机制：宪法表读取、基础表写入（`employee`）、todo list生成（`task_steps`）、状态推进、锁定。是验证整个系统骨架的最佳起点。

### 9.4 新增建议：`meta_task_templates` 与 `task_steps` 的关系需显式定义
宪法表中的模板（`meta_task_templates`）是"类"，业务表中的跟进记录（`task_steps`）是"实例"。每条 `task_steps` 记录应有一个 `template_step_id` 外键，指回对应的模板步骤。这样才能：
- 知道哪些步骤是必须的（来自模板）
- 哪些步骤是临时追加的（无模板来源）
- 业务变更时，历史记录不受影响

## 10. 系统核心原则（不变）

| 原则 | 说明 |
|------|------|
| AI只能按规则执行 | 所有行为必须有宪法表中的对应规则 |
| 遇到卡点就报告 | 缺信息、条件不满足，必须上报，不得猜测 |
| 不能自行决策 | 遇到规则未覆盖的情况，停止并等待人工指示 |
| 任何判断必须有出处 | 每个操作都有 `rule_id` 和原始证据支撑 |
