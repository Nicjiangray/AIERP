## 1. 这次「整理」做了什么、没做什么

| 做了 | 没做（刻意避免） |
|------|------------------|
| 新增 **`docs/` 文档**：你能看懂的地图 + 给研发用的主路径清单 | **没有**大规模改代码、**没有**移动目录（避免一次改坏线上行为） |
| 在 **`README.md` 顶部**加了一行入口，方便找到 `docs/` | **没有**删除历史 SQL 或旧文件（历史脚本可能仍被老环境引用） |

原则：**先写清楚、再小步改代码**；大重构要等测试与排期。

---

## 2. 用户从说话到入库（业务主流程，一句话）

用户在前端聊天 → 后端识别**意图**（查数据 / 建客户 / 建合同等）→ 需要落库时先出**预览**，用户点**确认** → 再真正写入 PostgreSQL。

你可以把「意图」「预览」「确认」当成产品上的三道闸：**不该自动写入的，必须经过确认**。

---

## 3. 仓库里几块「板子」各管什么（便于对齐需求）

| 板块 | 你可以怎么理解 | 和需求的对应关系 |
|------|----------------|------------------|
| **前端** `frontend/src/` | 聊天界面、表格、确认按钮 | 交互、文案、错误提示展示 |
| **后端入口** `main.py` | 唯一 HTTP 入口：`/ai/chat`、`/ai/confirm` | 接口契约、会话、反馈 |
| **引擎** `engine/` | 意图、收集参数、工具执行、提交预览、确认写库 | 业务规则、「能不能这样改」多半在这里 |
| **数据库脚本** `constitution/` | 表结构、工作流配置、工具声明的种子数据 | **改业务规则常要配 SQL + 同步脚本**，不是只改 Python |
| **脚本** `scripts/` | 同步向量、跑测试 | 发布前检查、回归 |

---

## 4. 协作时建议你盯的 4 件事

1. **主路径是否清晰**：新功能是否走「聊天 → 预览 → 确认」，有没有偷偷自动写库。  
2. **配置与数据**：改意图、改工具名、改合同规则，往往要动**数据库里的配置** + 跑说明文档里的命令，不只是改界面。  
3. **验收标准**：至少 **`scripts/test_e2e_chat.py` 能跑通**（需本机数据库 + LLM）；关键场景应有人工验收清单。  
4. **技术债排期**：见 **`docs/技术主路径与整理清单.md`** 里的「后续可排期项」——适合放进 backlog，不要指望一次做完。

---

## 5. 风险提醒（不用懂技术，但要知会团队）

- **`.env`** 里有密钥，**不要提交到 Git**；换模型、换 API 会影响稳定性和费用。  
- **`constitution/` 里 SQL** 多在正式库执行过；随意删文件可能导致新环境装不起来——**删改前让研发评估**。  
- **异常断电**可能导致本机 PostgreSQL 起不来，研发可按 `CLAUDE.md` 里「启动方式」旁的 PostgreSQL 说明处理。
